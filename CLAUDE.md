# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Build the solution: `dotnet build WG.AP.Automation.slnx`
- **`WG.AP.Database` is built by both `dotnet` and Visual Studio, and the two disagree by default.** Two things keep it working, and both look deletable if you don't know why they are there:
  - **`WG.AP.Database/Directory.Build.props` splits `obj\`.** `Microsoft.Build.Sql` picks its TFM from the MSBuild runtime — `netstandard2.1` under `dotnet`, `net472` under VS. Sharing one `obj\` meant whichever restored last won and the other failed with `project.assets.json doesn't have a target for 'net472'` (or for `netstandard2.1`), flipping back on every Clean. That file redirects `BaseIntermediateOutputPath` to `obj\dotnet\` or `obj\vs\`, so the two restores stop overwriting each other. It has to be a `Directory.Build.props` — `BaseIntermediateOutputPath` is read by `Microsoft.Common.props` before the `.sqlproj` body is evaluated. `bin\` stays shared so the dacpac keeps its documented path. The `<Build Remove="obj\**\*.sql" />` lines in the `.sqlproj` are part of this: the SDK's glob only excludes the *current* build's `obj`, so each toolchain would otherwise pick up the other's generated `postdeploy.sql` and fail with `SQL71006`.
  - **`TreatAsLocalProperty` plus the `SSDTPath`/`SqlServerRedistPath` override in the `.sqlproj`.** VS resolves `SqlBuildTask` from the DacFx bundled in the IDE (170.4.53.0 in VS 18) instead of the one this SDK ships (170.4.83.3). The older task has no `AutomaticIndexCompaction` parameter, so the build dies with `SQL04063`/`SQL04064`. Three details make the fix work, and each one was a wrong turn first: it sets **`SqlServerRedistPath`** (the property that actually picks the assembly), not just `SSDTPath`; it uses **`$(SdkBinariesPath)`**, not `$(NETFrameworkTargetsPath)` — the latter reads correctly inside `Sdk.props` but MSBuild's common targets later overwrite it with a path to a `.targets` *file*; and it needs **`TreatAsLocalProperty`** on the `<Project>` element, because VS passes both as *global* properties and a `<PropertyGroup>` cannot override a global — the assignment is ignored silently, working from the CLI while changing nothing in the IDE. Verify a change here with `MSBuild.exe <proj> -getProperty:SSDTPath,SqlServerRedistPath` rather than by reading the file.
- Run all tests: `dotnet test WG.AP.Tests/WG.AP.Tests.csproj`
- Run a single test: `dotnet test WG.AP.Tests/WG.AP.Tests.csproj --filter "FullyQualifiedName~GraphMailboxProcessorTests.MoveMessageAsync_PreservesTheImmutableId_AndTheMessageIsReadableByItAfterTheMove"`
- Run the console app: `dotnet run --project WG.AP.Processing`. `WG.AP.Processing/Properties/launchSettings.json` is the **only** place `DOTNET_ENVIRONMENT=Development` is set (it is set nowhere at user or machine scope), and both an IDE F5 run **and** a plain CLI `dotnet run` apply it — `dotnet run` reads the first `commandName: Project` profile unless you pass `--no-launch-profile`. Running the built `WG.AP.Processor.exe` directly does **not**: `launchSettings.json` is a dev-time file that is never copied to the output, so the exe defaults to `Production` and loads `appsettings.Production.json` unless the variable is set in its environment. That is the case the eventual scheduled task falls into. It runs from any working directory: `Program.cs` pins `ContentRootPath` to `AppContext.BaseDirectory`, because the default is the *current* directory and the appsettings files live next to the executable — so `dotnet run` from the repo root, and the eventual scheduled task with no "Start in" set, would otherwise read no config at all and fail as though the settings were missing.
- CI (`.github/workflows/unit-tests.yml`) runs on PRs into `development`/`master`/`main`: restores, builds, and tests only `WG.AP.Tests.csproj` in Release config.

**Known repo state:** `WG.AP.Email/Class1.cs` is leftover scaffold code — an empty class holding a commented-out sketch that calls methods which don't exist on `IMailSource`. Because that body is commented out it **compiles cleanly**, so it no longer blocks `dotnet build`/`dotnet test` and needs no renaming aside to verify a build. (It did block the build while the sketch was live; that is no longer the case.) The repo owner has asked for it to be left in place — they'll delete it themselves. Do not delete or "fix" it.

## Architecture

This is a .NET 10 solution (`WG.AP.Automation.slnx`) automating AP (accounts payable) invoice intake from a mailbox. Mailbox intake, PDF invoice extraction, and the SQL database that records all of it are implemented. Pace integration and reporting are still scaffolds.

**Projects:**
- `WG.AP.Core` — dependency-free abstractions only (`Abstractions/IMailSource.cs`, `IMailSender.cs`, plus DTOs: `MailMessageSummary`, `MailAttachmentSummary`, `MailDestinationFolder`, `MailSendRequest`, `MailboxDeltaResult`, `IMailboxSyncStateStore`). No reference to `Microsoft.Graph`/`Azure.Identity` — downstream consumers depend on the contract, not the Graph SDK.
- `WG.AP.Email` — the Graph-backed implementation: `GraphMailboxProcessor` (implements both `IMailSource` and `IMailSender`), `MailboxSyncProcessor` (delta-sync orchestrator), `MailboxOptions`.
- `WG.AP.DataAccess` — Dapper repositories over the AP database (`SqlConnectionFactory`, `MailMessageRepository`, `MailAttachmentRepository`, `InvoiceRepository`, `ClientRepository`, `ExtractionPromptRepository`, `ProcessingRunRepository`, `ApplicationLogRepository`), the `SqlMailboxSyncStateStore`, and `AttachmentFileStore` (writes attachment bytes to the UNC share). No EF Core — hand-written SQL only. `FileMailboxSyncStateStore` and `DualMailboxSyncStateStore` are temporary: the file store is a fallback for the first week after cutover, then both go.
- `WG.AP.Database` — the SQL Database Project (`Microsoft.Build.Sql` SDK, **2.2.0 or later required** — 1.x cannot restore under the .NET 10 SDK). 10 tables, seeds as `MERGE` in post-deployment, Dev/Prod publish profiles, plus `Tests/constraints.sql`. See `docs/references/database-schema.md`.
- `WG.AP.Processing` (assembly/namespace `WG.AP.Processor`, project folder `WG.AP.Processing` — the names don't match) — the entry point. A console app hosted via `Host.CreateApplicationBuilder`; `Program.cs` wires up all DI and config; `APProcessor` is the top-level orchestrator; `Logging/` holds a custom file-logging provider.
- `WG.AP.Invoice` — PDF invoice extraction: `PdfInvoiceFieldExtractor` (deterministic regex tier, Ollama fallback), `SanmarPdfHeaderExtractor`, `OllamaClient`, `InvoiceFieldsJsonParser`, and the `InvoiceFields`/`ExtractionRequest` models. Excel/manifest handling was removed — attachments still arrive, nothing reads them.
- `WG.AP.Reporting`, `WG.AP.Integrations.Pace` — still empty scaffolds, wired with project references but no implementation.
- `WG.AP.Tests` — xunit tests referencing every other project. `Email/FakeGraphHandler.cs` fakes the Graph HTTP layer (routes by method + URL match) so Graph-dependent tests run with no real tenant, credentials, or network access.

**The mailbox pipeline** (`Program.cs` → `APProcessor` → `MailboxSyncProcessor` → `GraphMailboxProcessor` → `IMailboxSyncStateStore`):

1. `Program.cs` binds `MailboxOptions`/`MailboxSyncStateOptions`/`FileLoggerOptions`, builds a `GraphServiceClient` from app-only `ClientSecretCredential`, and registers `GraphMailboxProcessor` as both `IMailSource` and `IMailSender`, `FileMailboxSyncStateStore` as `IMailboxSyncStateStore`, `MailboxSyncProcessor`, and `APProcessor`.
2. `APProcessor.ProcessInvoicesAsync` is the single entry point: `ValidateAuthAsync` (auth smoke test) → `EnsureFoldersExistAsync` (creates `Processed`/`Errors`/`NeedsReview` under Inbox if missing) → `MailboxSyncProcessor.GetNewMessagesAsync` (delta-fetch only new/changed mail) → per-message logging → `MailboxSyncProcessor.CommitAsync` (persist the new delta link) — all inside one top-level try/catch that sets `Environment.ExitCode = 1` on failure, since this runs unattended under Windows Task Scheduler with no process supervisor.
3. Delta sync: `GraphMailboxProcessor.GetInboxDeltaAsync` calls Graph's mail delta query (`.../mailFolders('inbox')/messages/delta()`), paginating via `OdataNextLink` until a page carries `OdataDeltaLink`, and drops tombstoned (`@removed`) entries. **The new delta link is committed only after the caller has finished handling the whole batch, not immediately after fetching** — so a crash mid-processing re-delivers the same batch next run instead of silently losing it. Don't move that commit earlier without preserving this property.
4. State persistence: `dbo.MailboxSyncState`, one row per mailbox, keyed on the **mailbox Entra object id** (`MailboxOptions.MailboxId`) rather than the address — so renaming the AP mailbox does not start a fresh delta sync. `DualMailboxSyncStateStore` also writes the old JSON file as a week-one fallback.

**Auth & immutable ids:** app-only (client credentials), not delegated — meant to run unattended. Every Graph request adds a `Prefer: IdType="ImmutableId"` header (`GraphMailboxProcessor.ApplyImmutableId`) because a message's default id changes when it moves folders; without the immutable id, both the move-then-reread guarantee and future dedup logic would break the moment a message got filed into a destination folder.

**Logging:** `Program.cs` registers a console provider *and* a custom `WG.AP.Processor.Logging.FileLoggerProvider`, so every `ILogger<T>` call anywhere in the app is written both to the console and to a daily text file under `%ProgramData%\WG.AP.Automation\Logs\` (path/level configurable via the `FileLogging` config section) — this exists because the process runs unattended with no console to watch. `FileLogger.Log` swallows its own I/O failures so a broken log can never take down mailbox processing. **When adding new code that talks to an external system** (Graph, a future DB, a future integration), follow the established pattern in `GraphMailboxProcessor.cs`: wrap the call in try/catch, `logger.LogError(exception, "<message with the relevant id(s) — mailbox/message/attachment/etc.>")`, then rethrow, so the file log always shows exactly where a failure happened. Note the one wrinkle: C# disallows `yield return` inside a `try` block that has a `catch`, so an `IAsyncEnumerable` method (like `EnumerateInboxAsync`) needs its Graph calls split into non-iterator helper methods that each do their own try/catch/log/rethrow.

**Config:** `MailboxOptions`, `MailboxSyncStateOptions`, `FileLoggerOptions`, `SqlLoggerOptions`, `OllamaOptions`, `DatabaseOptions`, and `FileStorageOptions` all follow the same shape — bound via `IOptions<T>` from a named `SectionName`, with `appsettings.{Environment}.json` overrides. **Every `appsettings*.json` is tracked by git and must stay free of credentials** — the dev database is reached with a SQL login, so secret-bearing values (`Database:ConnectionString`, and `Mailbox:ClientSecret` once Graph is configured) go in `WG.AP.Processing/appsettings.Development.local.json`, which is gitignored (`appsettings.*.local.json`), loaded last and only in Development, and optional so CI and the server do not need it. `appsettings.Development.local.json.template` is committed next to it and documents the shape. Two hard guards on `MailboxOptions`: `IsTestMailbox` must be `true` (this adapter moves mail into subfolders and must never target the live AP inbox), and `MailboxId` must not be `Guid.Empty` (it is the key every stored row and the delta cursor hang off, and an empty value would silently share a namespace across mailboxes). All seven options types are validated **before any work starts**, but note *how*: `.ValidateOnStart()` alone does nothing here, because it registers a hosted service that runs from `host.StartAsync()` and this host is never started — `Program.cs` resolves `APProcessor` and awaits it directly. The line that actually enforces it is `host.Services.GetRequiredService<IStartupValidator>().Validate();` right after `builder.Build()`. **Do not delete it as redundant** — without it only `MailboxOptions` is checked, and only incidentally, because the Development log block reads its `.Value`; a wrong `Database:ConnectionString` would then surface only after auth, folder creation and a delta fetch had already run. Multiple failures arrive as an `AggregateException` of `OptionsValidationException`s, caught by the top-level handler that logs and sets `Environment.ExitCode = 1`. `FileStorageOptions` is the one that does not use an inline `.Validate()` lambda: `FileStorageOptionsValidator` (an `IValidateOptions<T>` beside the options class in `AttachmentFileStore.cs`) checks the root **exists and is actually writable**, by writing a probe file and deleting it — "not an empty string" says nothing about a UNC share that is unreachable or read-only to the service account. The root is deliberately **not** created on demand, unlike the `yyyy\MM` folders under it: with 7-year retention, a mistyped path must fail at startup rather than quietly become a new empty folder nobody backs up. Two consequences worth knowing — startup makes a round trip to the share, and an unreachable UNC path blocks for the OS timeout before failing.

**Database:** see `docs/references/database-schema.md` — it covers deployment, which guarantee lives where, and the traps. Two that bite from the C# side: these tables carry indexes on persisted computed columns, so any client writing to them needs `QUOTED_IDENTIFIER` and `ANSI_NULLS` ON (fine for `Microsoft.Data.SqlClient`, **not** for `SQLCMD` without `-I`); and Dapper cannot bind `DateOnly` without the handlers in `DapperTypeHandlers`, registered from `SqlConnectionFactory`'s static constructor because every query opens its connection there.

**Testing against a database:** `WG.AP.Tests/DataAccess/SqlRepositoryTests.cs` runs the repositories against a real server, opt-in via `AP_TEST_DB_CONNECTION`. They are integration tests deliberately — the guarantees are enforced by unique indexes and `WHERE` clauses, so a fake would just be a second, wrong implementation of the rule.

**The no-reprocess rule is a database constraint, not a convention.** `lkup.Status.IsFinal` plus `UQ_MailMessage_MessageKeyHash` are what make "an email is never processed twice" true; `MailMessageRepository.DiscoverAndClaimAsync` is the only place a message may be claimed, and `@@ROWCOUNT = 0` there means *do not parse, do not move*. A transient failure has no status — it is the **absence** of a final state, so retry works through the delta link never being committed, exactly as it did before the database existed. Read `docs/references/database-schema.md` before changing any of this; several of its constraints exist because a plausible-looking simplification is wrong (a filtered index cannot reference a computed column; `[Total] > 0` alone lets NULL through; `BETWEEN` and `IN` in a CHECK churn on every publish).

See `docs/GraphMailboxProcessor.md` for a deeper reference on the Graph adapter (method-by-method behavior, Entra ID prerequisites, known follow-ups like large-attachment streaming) — it predates the delta-sync and file-logging work described above, so treat it as background on the original adapter rather than the current end-to-end pipeline.
